# TRDD-94e06820 — Body-vs-frontmatter tool-consistency (CRITICAL)

**Filename:** `design/tasks/TRDD-20260522_175413+0200-94e06820-body-tool-consistency.md`
**Tracked in:** this repo (design/tasks/ is git-tracked)

## Source

User requirement (verbatim, condensed):

> Of course there is a case where the problem becomes a CRITICAL: if the
> skill or agent file body actually CONTAINS a tool usage even if the
> frontmatter is allowing no tools with `[]`, or simply contains tools not
> declared in the `allowed-tools` field. That is a critical issue, since the
> attempt at using the tool will fail, making the skill or agent fail silently.

Surfaced while finalizing the "empty `allowed-tools: []` = WARNING (valid,
chat-only)" recalibration. The user's point: an empty (or restrictive)
declaration combined with a body that *uses* a non-declared tool is not a
style nit — it is a runtime correctness bug. The tool call fails, and the
skill/agent fails **silently**.

## Core rule

When a component declares an `allowed-tools` (skills/commands) or `tools`
(agents) field, the set of tools the **body** actually invokes MUST be a
subset of the declared set. Two violation classes, both **CRITICAL**:

1. **Empty declaration + body uses a tool.** `allowed-tools: []` / `tools: []`
   means "no tools" (chat-only). If the body invokes ANY tool → CRITICAL.
2. **Non-empty declaration + body uses an undeclared tool.** Declared
   `[Read, Grep]` but the body invokes `Bash(...)` → CRITICAL.

When the field is **ABSENT**, all tools are allowed → this check is SKIPPED
(no possible contradiction).

Interaction with the v2.101.5 empty-`[]` WARNING (already shipped in this
change set):

| declared set | body uses a tool? | verdict |
|---|---|---|
| absent | (any) | no finding (all tools allowed) |
| empty `[]` | NO | WARNING (valid chat-only declaration) |
| empty `[]` | YES | **CRITICAL** (silent-failure contradiction; subsumes the WARNING) |
| non-empty | only declared tools | PASSED |
| non-empty | an undeclared tool | **CRITICAL** (per undeclared tool) |

## The hard part — "body uses a tool" detection (FP risk)

Skill/agent bodies are prose+markdown that **mention** tools constantly
("use the Read tool", "invoke `Skill({...})`", fenced `Bash` examples). The
detector must separate genuine **usage instructions** from **documentation
mentions**, because a false CRITICAL **blocks a legitimate publish** (NIT→
CRITICAL all block per the user's publish gate).

### Detection signal (high precision)

A tool *invocation* in a Claude-Code skill/agent body is the function-call
syntax, not a bare noun:

* `\b<KnownTool>\s*\(`  — e.g. `Read(`, `Bash(`, `Edit(`, `Grep(`,
  `Skill({`, `Agent({`, `Task({`, `AskUserQuestion({`, `WebFetch(`.
* `mcp__[a-z0-9_]+\s*\(` — MCP tool calls.
* `<KnownTool>` MUST be in `VALID_TOOLS` (cpv_validation_common.py:549) so
  random `Foo(` never matches.

This naturally excludes prose ("the Read tool", "run bash") because there is
no `(` immediately after the name.

### Subset / equivalence logic

* Declared bare `Bash` OR scoped `Bash(git:*)` → satisfies any `Bash(`
  usage in the body (scoping is a refinement, not a different tool).
* `Task` and `Agent` are aliases (Task renamed → Agent in v2.1.63) → each
  satisfies the other.
* MCP: declared `mcp__server__tool` satisfies a `mcp__server__tool(` body
  call; a declared bare server prefix satisfies its tools.

### FP-handling — THE design decision (needs user sign-off)

Reuse `scripts/_skillaudit_markdown_context.py::classify()` (fence-aware:
returns `safe_doc` for prose / inline-code, `code_fence_neutral` for code
fences, `unknown` otherwise) on each match's line. Three candidate policies:

* **Option A — Strict.** Any invocation-syntax match for an undeclared tool
  → CRITICAL, regardless of context. Highest recall, highest FP risk
  (documentation skills that show tool syntax would false-fire).
* **Option B — Balanced (RECOMMENDED).** Match in an instruction context
  (code fence, or imperative line outside prose) → CRITICAL. Match that is
  pure prose documentation (`safe_doc`) → DEMOTE to WARNING ("body mentions
  an undeclared tool — verify it is documentation, not usage"). This catches
  the real silent-failure bug while letting documentation mentions pass with
  a non-blocking nudge.
* **Option C — Conservative.** Implement only violation-class #1 (empty `[]`
  * body invocation) now — the clearest, highest-value case — and defer the
  non-empty subset case to a follow-up after FP-tuning against real plugins.

The empty-`[]` case is the strongest signal regardless of option: a component
that explicitly declares "no tools" has no legitimate reason to show tool
*invocation* syntax in its body.

## Where it lives

A single shared helper in `scripts/cpv_validation_common.py`:

```python
def validate_body_tool_usage(
    body: str,
    declared_tools: list[str] | None,   # None == field absent → caller skips
    report: <ReportType>,
    *, filename: str = "SKILL.md",
) -> None
```

Wired into the body-validation pass of all four validators that already
parse the body and run `validate_<thing>(body, report)`:

* `validate_skill_comprehensive.py`
* `validate_skill.py`
* `validate_command.py` (commands also carry `allowed-tools` + a body — same
  silent-failure risk; user said "skill or agent" but the rule is identical
  for commands)
* `validate_agent.py`

The caller passes `declared_tools=None` when the field is absent (skip),
`[]` when empty, or the parsed list otherwise.

## Outcome note (Phase 1 caught real bugs)

On its first run the check flagged **10 of CPV's own v2.101.0 batch commands**
(`commands/cpv-batch-*.md`): each declared `allowed-tools: Read, Bash, Glob,
Grep` but dispatches sub-agents via the `Agent` tool in a fenced block — a real
silent-failure bug (the dispatch would be denied at runtime). These shipped
because nothing strictly validated CPV's own commands for CRITICALs; the new
self-consistency regression guards close that gap.

**Final resolution (superseded the intermediate fix):** the intermediate fix
added `Agent` to each command's `allowed-tools`. The user then directed that
ALL tools be allowed in every CPV command, skill, and agent — so the
`allowed-tools`/`tools` field was removed from ALL components (41 skills, 1
agent, 12 commands; `cpv-pre-install-scan.md` already had none). An absent field
means all tools allowed, which resolves the dispatch bug (commands inherit
`Agent`) AND opts CPV's own components out of the body-consistency check (absent
→ skipped). The check still protects every OTHER plugin CPV validates. The
self-consistency guards now pass by skip and remain as latent regression guards
against any future re-introduction of a restrictive field.

## FINALIZED DECISIONS (2026-05-22, after user direction)

The user chose **Balanced** FP handling and added three requirements:

1. **Authoritative tool list** — fetched from
   `https://code.claude.com/docs/en/tools-reference.md`. The canonical
   built-in tool identifiers (PascalCase) are baked into the new module as
   `CANONICAL_TOOLS`:
   `Agent, AskUserQuestion, Bash, CronCreate, CronDelete, CronList, Edit,
   EnterPlanMode, EnterWorktree, ExitPlanMode, ExitWorktree, Glob, Grep,
   ListMcpResourcesTool, LSP, Monitor, NotebookEdit, PowerShell,
   PushNotification, Read, ReadMcpResourceTool, RemoteTrigger,
   ScheduleWakeup, SendMessage, ShareOnboardingGuide, Skill, TaskCreate,
   TaskGet, TaskList, TaskOutput, TaskStop, TaskUpdate, TeamCreate,
   TeamDelete, TodoWrite, ToolSearch, WaitForMcpServers, WebFetch,
   WebSearch, Write` plus the historical alias `Task` (→ `Agent`).
2. **Flag every MCP usage not explicitly allowed** — body `mcp__server__tool`
   calls matched against declared `mcp__*` patterns with glob semantics
   (`mcp__github__*`, bare-server `mcp__github`, exact `mcp__github__get`).
3. **Proper permission-glob matching** — the `allowed-tools` field uses the
   full settings.json permission grammar `ToolName(specifier)`. Matching uses
   a real glob library (`fnmatch` for command/name/MCP globs; `pathspec` for
   path specifiers), never naive string equality.

### Permission grammar facts (from tools-reference.md)

* Rule form `ToolName(specifier)`; bare `ToolName` = whole-tool grant.
* Specifier formats shared across tool groups:
  * `Bash(npm run *)` → Bash **and** Monitor (Monitor reuses Bash rules).
  * `Read(~/x/**)` → Read, Grep, Glob, LSP (path grammar).
  * `Edit(/src/**)` → Edit, Write, NotebookEdit (path grammar) — **and an
    `Edit(...)` grant also grants Read on the same path.**
  * `Skill(deploy *)` → Skill (name grammar).
  * `Agent(Explore)` → Agent (subagent-type grammar).
  * `WebFetch(domain:example.com)` → WebFetch (domain grammar).
  * `WebSearch` → no specifier.
* These cross-tool grants matter for FP avoidance: a declared `Bash(...)`
  rule grants the Monitor tool too; a declared `Read(...)` rule grants
  Grep/Glob/LSP; a declared `Edit(...)`/`Write(...)`/`NotebookEdit(...)`
  rule grants the others in its group **and** Read.

### Phase split

**Phase 1 (ship now) — tool-NAME + MCP level, the high-value low-FP core:**

* New module `scripts/cpv_tool_permission_match.py`:
  * `CANONICAL_TOOLS`, alias map, tool-group cross-grant map.
  * `parse_rule(rule) -> (tool, specifier|None)`.
  * `granted_tool_names(rules) -> set[str]` (expands cross-tool group grants
    * Edit→Read).
  * `mcp_usage_allowed(rules, mcp_call) -> bool` (fnmatch globbing).
  * `detect_body_usages(body) -> list[Usage(tool, line, in_fence, raw)]` —
    `\b<CanonicalTool>\s*\(`, `mcp__\w+__\w+`, and ```` ```bash ```` /
    ```` ```sh ```` fences (→ Bash usage).
* `validate_body_tool_consistency(frontmatter, body, report, *, filename)` in
  cpv_validation_common.py — skips when field absent; CRITICAL when declared
  set does not grant a used tool / MCP; severity demoted to WARNING when the
  usage line classifies as `safe_doc` (prose) per
  `_skillaudit_markdown_context.classify()`; empty `[]` + any real usage →
  CRITICAL.
* Wired into validate_skill_comprehensive.py, validate_skill.py,
  validate_command.py, validate_agent.py.

**Phase 2 (deferred) — specifier-level matching:** does a body's literal
`Bash(npm install)` / bash-fence command match the declared `Bash(git:*)`
scope; does a body file path match a declared `Read(~/x/**)` path glob
(pathspec). Deferred because reliably extracting a literal specifier from a
prose/markdown body is FP-prone; the tool-NAME + MCP level catches the
silent-failure bug the user described without that risk. Specifier mismatch,
when implemented, will be WARNING (extraction uncertainty), not CRITICAL.
