## 1. Why this TRDD exists

The user's instruction:
> "as for the hash/authentication procedure of the publish.py, this feature
> also need to be standardized, with some standard names and paths. as for
> the publish.py authentication standard, this feature also must be written
> in detail into a TRDD file and be left for the future."

Today every plugin's `publish.py` invents its own hash filename, its own
secret env-var names, its own keychain paths, and its own
GitHub-anchored integrity manifest URL. A user who ships 10 plugins ends
up with 10 subtly different conventions, and CPV's `cpv_integrity.py`
has to special-case each one.

This TRDD locks down a **single authentication and integrity standard**
that every plugin's publish.py — including CPV's own — adopts verbatim.

Defer implementation: TRDD-9065109a already enumerates the broader
zero-config publish architecture; this one is the auth/integrity slice
extracted into a focused spec so it can be reviewed and shipped
independently.

---

## 2. The eight surfaces that need standardization

| # | Surface | Today (per-plugin chaos) | Standard (this TRDD) |
|---|---|---|---|
| 1 | Self-hash manifest filename | `.cpv-self-hashes.json`, `.pss-hashes.json`, ad-hoc | **`.plugin-self-hashes.json`** at repo root |
| 2 | Hash compute script | `compute_cpv_self_hashes.py`, etc. | **`scripts/_plugin_compute_hashes.py`** (CPV ships canonical impl) |
| 3 | Hash verify module | `cpv_integrity.py`, etc. | **`scripts/_plugin_verify_hashes.py`** (CPV ships canonical impl) |
| 4 | GitHub-anchored URL pattern | per-plugin custom | **`https://raw.githubusercontent.com/<owner>/<repo>/v<version>/.plugin-self-hashes.json`** |
| 5 | GH PAT keychain entry | `gh auth`, `GITHUB_TOKEN`, ad-hoc | **`gh auth login` + `gh auth token`** (delegated to `gh` CLI; no plugin-managed secrets) |
| 6 | Plugin-shipped sensitive userConfig | per-plugin custom names | **`plugin.json.userConfig.<key>` with `sensitive: true`** (CC writes to OS keychain) |
| 7 | OpenRouter / 3rd-party API keys | env vars, .env, custom | **userConfig with `sensitive: true` + env-var fallback `<PLUGIN>_<KEY>`** |
| 8 | Per-version cache + freshness | per-plugin TTL choices | **`~/.cache/<plugin>/manifest-v<ver>.json`** with **1-hour TTL** |

Bottom line: the user's GH credentials live in `gh` (single source of
truth). Plugin-shipped secrets live in CC's keychain via `userConfig`.
The only thing the plugin's own publish.py manages is the **integrity
manifest** that proves the install hasn't been tampered with.

## 3. The integrity manifest — file format and lifecycle

### 3.1 Filename and location

**`<repo-root>/.plugin-self-hashes.json`**

- Single dot-prefixed file at repo root.
- Committed to git, shipped in the install.
- Generated by Gate 9 of the standard publish pipeline (see TRDD-9065109a §
  Phase 1) — i.e. by `scripts/_plugin_compute_hashes.py`.
- Read by `scripts/_plugin_verify_hashes.py` at every script entry point
  (mirror of CPV's current cpv_integrity.py at-import behavior).

### 3.2 JSON schema (v2 — replaces today's CPV-specific format)

```json
{
  "$schema": "https://raw.githubusercontent.com/Emasoft/claude-plugins-validation/main/schemas/plugin-self-hashes-v2.json",
  "format_version": 2,
  "plugin": {
    "name": "claude-plugins-validation",
    "version": "2.51.0",
    "owner": "Emasoft",
    "repo": "Emasoft/claude-plugins-validation"
  },
  "git": {
    "commit": "abc123def456...",
    "tag": "v2.51.0",
    "branch": "main"
  },
  "submodules": [
    {
      "path": "dev/tests",
      "url": "https://github.com/Emasoft/claude-plugins-validation-tests.git",
      "commit": "789xyz...",
      "shipped_in_install": false
    }
  ],
  "hashed_files": {
    "scripts/validate_plugin.py": "sha256-...",
    "scripts/validate_security.py": "sha256-...",
    "agents/plugin-fixer.md": "sha256-...",
    "skills/fix-validation/SKILL.md": "sha256-..."
  },
  "manifest_metadata": {
    "generated_at": "2026-05-02T22:00:00+02:00",
    "generated_by": "scripts/_plugin_compute_hashes.py v2.0",
    "hash_algorithm": "sha256",
    "scope": "runtime-bucket",
    "excluded_paths": [
      "tests/", "design/", "docs_dev/", "scripts_dev/",
      "reports/", "reports_dev/", ".git/", ".venv/", "__pycache__"
    ]
  }
}
```

### 3.3 What gets hashed (`scope: runtime-bucket`)

The hash list mirrors **everything that ships in the install** — i.e.
the runtime bucket from TRDD-793ac32a §3.1. Anything in `dev/`,
`tests/`, `design/`, gitignored folders, or excluded by the
strip-dev-parts config is **NOT hashed** because it doesn't ship.

### 3.4 Versioned URL convention

Every release's manifest is fetchable at:
```
https://raw.githubusercontent.com/<owner>/<repo>/v<version>/.plugin-self-hashes.json
```

`raw.githubusercontent.com` resolves the `v<version>` git tag — CDN-cached
once the tag exists, so verify calls are sub-second after the first fetch.

### 3.5 Local cache

`~/.cache/<plugin>/manifest-v<version>.json` — copied from the URL on
first read, refreshed every 1 hour. Override:
- `<PLUGIN>_SKIP_GITHUB_INTEGRITY=1` env var → bypass entirely (dev mode)
- `<PLUGIN>_REFRESH_INTEGRITY=1` → force re-fetch

## 4. The standard publish.py authentication chain

### 4.1 GitHub authentication

Single allowed mechanism: **`gh` CLI**, configured once via `gh auth
login` against the user's host (github.com or any GHES instance). Inside
publish.py:

```python
def _ensure_gh_auth() -> None:
    """Verify gh is authenticated for the current owner. Exit 1 if not."""
    res = subprocess.run(["gh", "auth", "status"], capture_output=True, text=True)
    if res.returncode != 0:
        fatal("gh CLI not authenticated. Run: gh auth login")
    # Verify the configured user can push to the target owner
    res = subprocess.run(
        ["gh", "api", f"repos/{owner}/{repo}", "--jq", ".permissions.push"],
        capture_output=True, text=True,
    )
    if res.returncode != 0 or res.stdout.strip() != "true":
        fatal(f"gh user has no push permission on {owner}/{repo}")
```

Forbidden in standard publish.py:
- Reading `GITHUB_TOKEN` from env.
- Writing PATs to disk.
- Using `git push https://<token>@github.com/...` URLs.
- Custom auth flows.

If the user wants to publish via a CI runner, they configure `gh` on
the runner — same as a workstation.

### 4.2 Plugin-shipped secrets via userConfig

Every plugin that needs to call third-party APIs (OpenRouter, OpenAI,
Anthropic, etc.) declares the credential in `plugin.json`:

```json
{
  "userConfig": {
    "openrouter_api_key": {
      "type": "string",
      "title": "OpenRouter API key",
      "description": "Used by mcp__llm-externalizer for remote model calls.",
      "sensitive": true,
      "required": false
    }
  }
}
```

Claude Code:
- Prompts at install time (or via `/plugin configure`).
- Stores in the OS keychain.
- Exports to MCP servers / hooks as `CLAUDE_PLUGIN_OPTION_OPENROUTER_API_KEY`.

The plugin's MCP server resolves `$OPENROUTER_API_KEY` and falls back
to `$CLAUDE_PLUGIN_OPTION_OPENROUTER_API_KEY` if the canonical name
isn't set — same pattern llm-externalizer uses today (memorialised in
`~/.claude/rules/use-llm-externalizer.md`).

### 4.3 Forbidden secret patterns in any plugin

CPV's validate_security already catches these; this TRDD just elevates
them to the standard:

- `.env` file committed to git (CRITICAL).
- API key embedded in a script or markdown (CRITICAL).
- Reading a secret from an unstandardized env-var name (MAJOR — must use
  the userConfig-derived name first).
- Plugin's publish.py reading `gh auth token` and stashing it anywhere
  (CRITICAL — only `gh` CLI subprocess calls allowed).

## 5. The standard publish.py — auth-related gates only

Excerpted from the broader 15-gate pipeline in TRDD-9065109a:

| Gate | Name | Auth-relevant action |
|---|---|---|
| 0 | Detect repo shape | `git config remote.origin.url` (read-only, no auth) |
| 1 | Verify clean tree | `git status --porcelain` (read-only) |
| 7 | Push commit + tag | `gh auth status` precheck → `git push origin main && git push origin v<ver>` |
| 8 | Push submodules | `gh auth status` precheck → `git submodule foreach 'git push'` |
| 9 | **Refresh `.plugin-self-hashes.json`** | `python scripts/_plugin_compute_hashes.py` (no auth) |
| 14 | Create GitHub release | `gh release create v<ver> --notes-file ...` (uses gh auth) |

No gate ever asks the user for a password, token, or any other secret
on stdin. Every secret is sourced from `gh auth` or `userConfig`.

## 6. Migration plan (when implemented)

### 6.1 CPV-specific renames

| Today | New |
|---|---|
| `.cpv-self-hashes.json` | `.plugin-self-hashes.json` |
| `scripts/compute_cpv_self_hashes.py` | `scripts/_plugin_compute_hashes.py` |
| `scripts/cpv_integrity.py` | `scripts/_plugin_verify_hashes.py` |
| Env var `CPV_SKIP_GITHUB_INTEGRITY` | `PLUGIN_SKIP_GITHUB_INTEGRITY` (CPV alias kept for 1 release) |

### 6.2 Plugin-creator changes

- Generated `publish.py` template uses the standard names from §2.
- `_plugin_compute_hashes.py` and `_plugin_verify_hashes.py` are vendored
  in every new plugin (or referenced as a vendored library — TBD in
  TRDD-9065109a §“canonical scripts”).
- Generated `plugin.json` includes a `userConfig` block stub when the
  user opts into "this plugin will need API keys".

### 6.3 Backwards compatibility

- For 1 release after this lands, `cpv_integrity.py` checks BOTH the
  new filename and the legacy `.cpv-self-hashes.json`. Stale legacy
  manifests trigger a one-line WARNING ("rename to
  .plugin-self-hashes.json — see TRDD-bbff5bc5") instead of a CRITICAL.
- Two releases later, the legacy fallback is removed.

## 8. Out of scope (deliberately deferred)

- **Multi-org publishing** — supporting `Emasoft` AND a corp account
  from the same publish.py invocation. This adds enough complexity to
  warrant its own TRDD when the need arises.
- **CI-side automated publishing** — GitHub Actions running publish.py
  on tag push. The standard works there (via `gh` configured in the
  runner) but the CI workflow itself is its own design problem.
- **Mirror to npm / pypi** — publish.py focuses on git+gh release; pkg
  registry mirroring is a separate pipeline.
- **Signing releases (sigstore, GPG)** — useful future addition, not in
  scope here.
