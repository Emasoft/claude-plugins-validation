# TRDD-aee35fd4 — Issue #25: canonical-pipeline publish.py / release.yml defects

**TRDD ID:** `aee35fd4-5c87-436a-a013-c1dff8a31da1`
**Filename:** `design/tasks/TRDD-aee35fd4-5c87-436a-a013-c1dff8a31da1-issue-25-canonical-pipeline-publish-defects.md`
**Tracked in:** this repo (design/tasks/ is git-tracked)
**Status:** Done (shipped in v2.87.1)
**Date:** 2026-05-15
**Source:** https://github.com/Emasoft/claude-plugins-validation/issues/25

## Symptom

`ai-maestro-plugin` was migrated to CPV's canonical pipeline. `validate_plugin`
reported the plugin structurally clean (0/0/0/0), yet the first real
`publish.py --patch` run hit a sequence of defects in the migrated
`publish.py`/`release.yml` and **crashed mid-publish**, leaving the v2.5.8
release half-finished. Four distinct defects identified by the reporter
against the migrated copy (which had been generated by an older CPV release).

| # | Defect | Reporter's read vs CPV v2.73.0 | Reality in CPV v2.87.0 (verified) |
|---|---|---|---|
| A | `_plugin_in_remote_marketplace` rejects `url` / `git` source forms | STILL LIVE in 2.73.0 | **STILL LIVE in 2.87.0** — `publish.py:885` |
| B | `git push origin HEAD --tags` crashes the pipeline on a diverged local tag | Appears fixed in 2.73.0 | **Confirmed gone** in 2.87.0; no regression guard existed |
| C | Doubled-backslash literals (`"\\t"`, `r"\\."`, `\\\"`) in CPV's `publish.py` | Appears fixed in 2.73.0 | CPV's own `publish.py` clean; **the `gen_publish_py` TEMPLATE still emits 5 bug instances** that the reporter never inspected |
| D | Migration installs `release.yml` running `uv run mypy` but does NOT reconcile a pre-existing `pyproject.toml`'s `dev` extra | Migration-reconciliation gap | **Gap confirmed** — `standardize_plugin` has audit/parse but no reconciliation |

## Decisions

* **Single canon, two copies.** `_plugin_in_remote_marketplace` lives in both
  `scripts/publish.py` (CPV's own) AND inside the `gen_publish_py` raw-string
  template that the migration writes to downstream plugins. Both copies got
  the same logic update; tests pin both.
* **pyproject is user-owned, so ALERT not auto-edit.** `pyproject.toml` is
  on the `_NEVER_FORCE_OVERWRITE` list (the user owns it; the migration must
  not stomp custom test/lint configuration). For Defect D the migration
  emits a loud `[ACTION REQUIRED]` block — the same UX shape as the
  v2.86.0 issue #23 secret-name alert — so the maintainer sees the gap
  before CI fails on first push.
* **Regression guards over verification.** Defects B and C were declared
  "appears fixed" by manual inspection of one source file. C in particular
  was only fixed in CPV's own `publish.py`; the migration template still
  carried 5 live bug instances the reporter could not see. Programmatic
  regression tests (B and C) over both copies catch this class going
  forward.

## Fix (v2.87.1)

### Defect A — accept `url` / `git` source forms (both copies)

`scripts/publish.py:870`, `scripts/generate_plugin_repo.py:2172` —
rewrite `_plugin_in_remote_marketplace`:

* accept `{"source": "github", "repo": "owner/repo"}` (previously the only
  accepted shape);
* accept `{"source": "url", "url": "https://github.com/owner/repo[.git]"}`
  by stripping `.git`, normalising trailing `/`, and matching the URL
  suffix `/<owner/repo>` (HTTPS) or `:<owner/repo>` (SSH);
* accept `{"source": "git", "url": "git@github.com:owner/repo[.git]"}`;
* bare string sources (`"./plugins/foo"`) remain local-directory entries
  and are not treated as remote registrations.

### Defect C — fix 5 live bug instances in the `gen_publish_py` template

The reporter's class-of-bug — doubled-backslash literals in a *raw* template
string — survived in 5 places inside `gen_publish_py`'s `r'''...'''` body:

| Location (template raw source) | Was | Should be | Effect of the bug in the generated `publish.py` |
|---|---|---|---|
| `_apply_notify_marketplace_overrides` regex (×2) | `r"^\\s*MARKETPLACE_(OWNER\|REPO):\\s*['\\\"]?…"` | `r"^\s*MARKETPLACE_(OWNER\|REPO):\s*[\"']?…"` | Regex matched literal `\s` instead of whitespace — owner/repo extraction always failed silently |
| `_gh_secret_exists` (×1) | `line.split("\\t", 1)` | `line.split("\t", 1)` | Split on literal `\t` instead of TAB — `gh secret list`'s TAB-separated output never parsed → secret falsely reported missing |
| Layout A/B JSON-hint cprints (×2) | `\\\"name\\\": \\\"…\\\"` | `\"name\": \"…\"` | Copy-paste hint printed `\"name\"` instead of `"name"` |

These are valid Python that does the wrong thing at runtime — no parser
catches them. The first plugin to migrate via CPV v2.87.0+ would have
shipped a `publish.py` carrying all 5. The regression test in §Tests
makes this class non-recurring.

### Defect D — `[ACTION REQUIRED]` dev-extras alert

`scripts/standardize_plugin.py` — new module-level constants and helper:

```python
_CANONICAL_DEV_EXTRA_TOOLS: tuple[str, ...] = ("mypy", "pytest", "ruff")
_CANONICAL_DEV_EXTRA_FLOORS: dict[str, str] = {...}
_WORKFLOW_PATHS_REQUIRING_DEV_EXTRAS = frozenset({
    ".github/workflows/release.yml",
    ".github/workflows/ci.yml",
})

def _canonical_dev_extras_missing(plugin_path: Path) -> list[str]:
    ...  # tomllib-based, fail-safe, returns [] when pyproject.toml is absent
```

`fix_missing_files` was extended: when the work-set includes one of the
two workflow files AND `_canonical_dev_extras_missing` is non-empty,
emit a multi-line `[ACTION REQUIRED]` block naming each missing tool
with its canonical version floor — so the maintainer can paste the
fix into their `dev` extra before the next push triggers CI.

### Defects B & C — regression guards

`tests/test_issue_25_publish_defects.py` includes line-level scanners that
run on BOTH CPV's `scripts/publish.py` and the live output of
`gen_publish_py(_params())`:

* B: refuses any `push` line that contains `--tags`.
* C: refuses doubled-backslash literal patterns (`"\\t"`, `'\\n'`,
  `r"\\."`, `\\\"`) outside docstrings / comments.

## Tests

`tests/test_issue_25_publish_defects.py` — 20 tests:

* **Defect A (8)** — github form, url form (with/without `.git`), git/SSH
  form, repo mismatch, `expected_repo=None`, bare string source, legacy
  `type` field. Each test runs against BOTH copies (CPV's and the
  template's, extracted via `ast.parse` + `compile`).
* **Defect B (2)** — no `push … --tags` in CPV's `publish.py` or the
  `gen_publish_py` template.
* **Defect C (2)** — no doubled-backslash literal in either copy.
* **Defect D (8)** — `_canonical_dev_extras_missing` returns: `[]` when no
  pyproject.toml; every tool when dev extra is empty; correct subset when
  partially declared; `[]` when complete; PEP-503 case-insensitive match.
  Plus integration tests via `fix_missing_files`: alert fires when
  release.yml is emitted and dev extra lacks mypy/pytest; suppressed when
  dev extra is complete; suppressed when no workflow file is emitted.

## Deferred / explicitly not implemented

* **Meta-problem: post-migration `publish.py --dry-run` smoke**. The
  reporter's strongest ask — have the canonical migration / validator
  run the very `publish.py` it installed in `--dry-run` mode so the
  green checkmark actually covers the release pipeline. Genuinely useful,
  but materially larger than this patch (needs sandboxed-git semantics,
  mock-marketplace-json, and a way to skip the gates that require a
  live remote). Tracked separately rather than crammed into v2.87.1.
* **Mass migration of plugins already scaffolded against ≤ v2.87.0**.
  Plugins generated before v2.87.1 carry the buggy template. They will
  pick up the fix on their next `standardize --fix --force-templates`
  run; CPV does not auto-rewrite installed copies.

## Lessons

* **Two copies of the same function is a recurring trap.** CPV's own
  `publish.py` and `gen_publish_py`'s template are sibling copies of
  the same logic. Manual inspection of one DOES NOT prove the other.
  Every test on `_plugin_in_remote_marketplace` here runs against both
  via `ast.parse` extraction — the only durable defence.
* **"Appears fixed by the rewrite" was wrong for C.** The reporter
  inspected v2.73.0's `publish.py` and saw the C-class bugs gone.
  The TEMPLATE that emits a `publish.py` to every downstream plugin
  still carried 5 live C-class bugs. The lesson: any "appears fixed"
  claim needs a programmatic test against every code-emission surface
  (the same way `validate_plugin` must cover every config-emission
  surface).
* **Migration ≠ scaffolding.** `gen_pyproject_toml` (new plugins) does
  the right thing — emits `mypy`/`pytest`/`pytest-cov`/`ruff` in `dev`.
  But `standardize_plugin.fix_missing_files` (migration of existing
  plugins) has a different responsibility: do not stomp user files,
  but DO alert when the user's file is incompatible with what we just
  installed. Defect D was the migration path missing this alert; the
  new `[ACTION REQUIRED]` block closes it without violating the
  "pyproject is user-owned" invariant.
