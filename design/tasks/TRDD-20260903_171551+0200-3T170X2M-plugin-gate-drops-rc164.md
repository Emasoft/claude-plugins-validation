# The plugin gate drops every RC-164 finding

## Symptom (settled in-process, 2026-09-03)

`validate_plugin` (the `--strict` gate `publish.py` Gate 3 runs) merges the
execution-class security pass through `_run_security_execclass_gate`, which keeps a
row only when `_extract_rule_id(message)` is in `_SECURITY_GATE_BUCKETS` Bucket A or in
`_EXECCLASS_RCE_RULE_IDS` (`scripts/validate_plugin.py:2525`). For an emitted
`RC-164: …` message the predicate returns:

```text
rule_id= 'RC-164' | in explicit set= False | bucketA= False | any 164 key in buckets= []
```

So every RC-164 finding (CRITICAL / MAJOR / INFO) has been dropped from plugin mode —
and therefore from every publish — since the guard shipped in v2.146.0. Only the
`security` subcommand emits it. A planted in-plugin script write in CPV's own
`scripts/bump_version.py` fired CRITICAL at the emitter and produced SUMMARY
`CRITICAL=0` in a cold strict plugin-mode self-validate.

Pre-existing at HEAD (identical SUMMARY on both trees for the janitor and CPV cache
roots). Found while central-verifying TRDD-ETDWX70R.

## Fix

Add `"RC-164"` to `_EXECCLASS_RCE_RULE_IDS` with a WHY comment (the copy-only in-plugin
write guard produces an unscanned in-plugin script that then runs — RCE-shaped), plus a
positive-control test through the REAL plugin gate: a planted write must reach the
`--strict` verdict, and the same tree without the probe must stay clean.

Check the sibling `RC-39` (persistence) with the same in-process predicate before
closing; record the answer here either way.

## Fleet impact (must be re-measured after RU0POO65, never assumed)

Emission-level census on 2026-09-03 (63 cached plugins, third-party rows, fold guard):
12 CRITICAL / 39 MAJOR / 4 MINOR would become publish-blocking. Several are the
prose-token captures of TRDD-RU0POO65, which is why that card is a hard prerequisite.

## Prerequisites found by the advisor verification (2026-09-03)

(a) With the self-scan ARMED, CPV's own tree emits blocking RC-164 rows from
its own fixtures — `tests/test_rc164_fold_tiers.py` lines 172, 280, 302, 306,
436 and `tests/test_cpv_write_sink_ast.py` lines 162, 163 (literal in-plugin
shell-redirect fixture strings; `effective_severity` demotes a `tests/` hit
only one notch, so these stay MAJOR/MINOR, not INFO). So admitting RC-164 to
the gate today would fail CPV's own `--strict` self-validate. The fix is
DEVITALIZED fixtures (assemble the shell shape at runtime so no source line
carries it verbatim — the v5.5.0 SSRF-fixture precedent) or a SHA-anchored
self-skip — NEVER a blanket `tests/` skip (the #75 ruling).

(b) The plugin-mode merge's level gate drops INFO, so T3 stays
security-mode-only even after the fix lands — acceptable, T3 is advisory
only and was never meant to block a publish.

(c) Third-party `tests/` dirs carry the same fixture class (see
TRDD-ETDWX70R's emission-AB report), so the "re-measure after RU0POO65" in
the Fleet impact section above must run in PLUGIN mode and count plugins
that would newly fail `--strict` — not just tally raw RC-164 rows.

## Prerequisite ordering (recorded 2026-09-04)

Fixing this card (adding `RC-164` to `_EXECCLASS_RCE_RULE_IDS` so the plugin
gate stops dropping every RC-164 row) will, in the same instant, make
TRDD-RU0POO65 live — that is the defect where the regex chmod path captures
prose tokens as file paths, producing false RC-164 rows. Today those two
defects cancel each other: the bad rows are generated but never surface at
the plugin gate. That mutual cancellation is NOT a safety property and must
not be relied on. Consequence: RU0POO65 must land BEFORE or IN THE SAME
change as this card, or the fix will surface a wave of false findings at the
publish gate. The dependency stays in `blocked-by:` only, where it was already
recorded — it was briefly also written into `npt:` and that was reverted, since
the second copy added nothing this card needed. (Whether the project's tooling
reconciles the two fields was not checked; this is a local choice, not a rule.)
