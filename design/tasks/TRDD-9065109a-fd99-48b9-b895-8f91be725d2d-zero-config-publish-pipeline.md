## User request (verbatim, 2026-05-02)

> "make a standard hash file, so there will be no need to customize the
> publish.py at all. not only that, but standardize everything else in
> the pipeline, including the use of git submodules if necessary (like
> for the perfect-skill-suggester plugin, where the gigabytes of rust
> source code and libs cannot be included in the plugin but only the
> build binary), and making the publish.py be able to detect all
> configuration data from the project config files, including multiple
> subfolders with independent gits, or special marketplaces that
> contain the plugin in a single repo, etc. everything is easily found
> in the project folder and with some heuristic it can be extracted by
> the publish.py to automatically get the right info for the plugin to
> publish, even if the script publish.py is the same identical in all
> plugins and all marketplaces."

## Goal

ONE identical `publish.py` byte-for-byte across every plugin and every
marketplace generated by CPV. The script reads only project-tree state
(no per-plugin customization, no environment variable overrides, no
generated boilerplate that varies between plugins). Auto-detection
covers every layout CPV currently supports plus the binary-bundle
submodule case.

## Why this matters (extends TRDD-b5e44619)

The previous TRDD already proposed promoting `publish.py` to a Python
module (`cpv.publish`) shared across plugins. This TRDD extends the
scope:

1. **Standard manifest format** — `.cpv-self-hashes.json` (the bug from
   issue #18) becomes the canonical manifest format that EVERY CPV-
   generated plugin/marketplace ships, computed identically. No
   per-plugin customization needed because the format is universal.

2. **Pipeline standardization beyond publish.py** — git hooks,
   workflows, CI configs, branch protection rules, release notes
   generation, marketplace dispatch — all driven from a single
   canonical source.

3. **Submodule-bundled plugins** — when source code is too large to
   ship via the marketplace (perfect-skill-suggester ships a Rust
   binary built from a 2-GB workspace), the plugin includes only the
   compiled artifact PLUS a `.gitmodules` pointer to the source repo
   for build reproducibility. publish.py understands this pattern.

4. **Auto-detected layouts** — single plugin, marketplace hub, nested
   monorepo, marketplace-in-plugin, AND new patterns like
   "workspace with N independent git subfolders" or "monorepo with
   submodules pointing at external plugin sources."

5. **Zero-config promise** — copy `publish.py` and a one-liner
   bootstrap into any project; running `publish.py` Just Works.

## High-level architecture

### A. Universal manifest format — `.cpv-self-hashes.json`

Standardized across every CPV-shipped repo (plugin OR marketplace):

```json
{
  "version": 2,
  "format": "cpv-hash-manifest-v2",
  "computed_at": "2026-05-02T22:00:00+02:00",
  "computed_by": "scripts/compute_cpv_self_hashes.py",
  "purpose": "Tamper-detection manifest. Every file's SHA256 must match at install.",
  "git": {
    "tag": "v2.50.2",
    "sha": "b6b8824…",
    "remote": "https://github.com/Emasoft/claude-plugins-validation.git"
  },
  "files": {
    "scripts/publish.py": "sha256:…",
    "scripts/validate_plugin.py": "sha256:…",
    …
  },
  "submodules": {
    "external/lib-rust": {
      "url": "https://github.com/example/lib-rust.git",
      "sha": "abc123…",
      "purpose": "Source-of-truth for the bundled binary at servers/lib-rust"
    }
  }
}
```

Key change vs current format: add `git`, `submodules`, and `version`
fields. Future-compat ready.

### B. Auto-detection: `cpv.publish.detect_repo_shape(root) -> RepoShape`

A single classifier function returns one of:

| Shape ID | Detection signals | Examples |
|----------|------------------|----------|
| `single-plugin` | `.claude-plugin/plugin.json` only | most plugins |
| `marketplace-hub` | `.claude-plugin/marketplace.json` only, no plugin.json | emasoft-plugins repo |
| `nested-monorepo` | both, plus `plugins/<name>/` subdirs each with own `.claude-plugin/` | Layout B |
| `marketplace-in-plugin` | both at root, single self-entry source `./` | Layout C, single-plugin repos that are also their own marketplace |
| `workspace-multi-git` | multiple subfolders, each with its OWN `.git/` AND `.claude-plugin/` | dev workspaces with several plugin repos cloned side-by-side |
| `submodule-bundle` | `.gitmodules` declares one or more submodules referenced by the plugin's manifest (e.g. binary built from submodule-tracked source) | perfect-skill-suggester |
| `unknown` | none of the above | error: not a CPV-managed repo |

### C. Auto-detected configuration data

Every value publish.py needs comes from the tree:

| Config item | Auto-detection source |
|-------------|----------------------|
| Plugin name | `.claude-plugin/plugin.json` `name` |
| Plugin version | `.claude-plugin/plugin.json` `version` |
| Author / email | `.claude-plugin/plugin.json` `author` (or git config fallback) |
| GitHub remote (owner/repo) | `git remote get-url origin` |
| Marketplace owner/repo | `.github/workflows/notify-marketplace.yml` env vars OR neighbouring `marketplace.json` |
| MARKETPLACE_PAT secret name | hard-coded constant `MARKETPLACE_PAT` (already standard) |
| Branch protection ruleset | `.github/branch-rules.json` (auto-generated) |
| Release notes template | `cliff.toml` (existing) |
| Pre-push hook script | `git-hooks/pre-push` (existing) |
| Submodule paths | `.gitmodules` |
| Bundled binary path | `plugin.json.servers[*].command` reference |
| Layout type | computed from `detect_repo_shape()` |

No env var fallbacks needed for any of these — they all live in the
tree.

### D. Submodule-bundle support (the perfect-skill-suggester case)

When `detect_repo_shape() == 'submodule-bundle'`:

1. publish.py runs `git submodule status` and verifies every submodule
   referenced by `plugin.json.servers[*]` is initialized.
2. If the bundled binary is missing, publish.py invokes the build
   script (auto-detected via `.cpv/build-bundled-binary.sh` or
   `Makefile` target `bundle-binary`) and rebuilds it.
3. The built binary's SHA256 lands in the manifest; the SOURCE submodule
   commit SHA also lands in `manifest.submodules[name].sha`.
4. End users who install the plugin get the binary only — they don't
   clone the submodule. Maintainers who need source can run
   `git submodule update --init --recursive` after cloning the plugin
   repo.

### E. Workspace-multi-git support

When `detect_repo_shape() == 'workspace-multi-git'`:

1. publish.py prints a numbered Unicode table listing every detected
   plugin/marketplace in the workspace.
2. User picks one (numbered choice, `0` to cancel).
3. publish.py recurses into the selected subfolder and re-runs from
   there with the auto-detection now seeing a single-plugin shape.

### F. ZERO per-plugin publish.py customization

The wrapper at `scripts/publish.py` in every plugin becomes:

```python
#!/usr/bin/env python3
# Standard CPV publish wrapper — DO NOT MODIFY.
# Behaviour is fully driven by .claude-plugin/plugin.json, .gitmodules,
# .github/workflows/, and git remote state. Customization happens via
# config files, never by editing this script.
from cpv.publish import main
import sys
sys.exit(main())
```

That wrapper is identical across every plugin. CPV ships the actual
logic in the importable `cpv.publish` module.

### G. Standard hash-file generation

`scripts/compute_cpv_self_hashes.py` becomes a thin wrapper too:

```python
#!/usr/bin/env python3
from cpv.hash_manifest import compute_and_write_manifest
import sys
sys.exit(compute_and_write_manifest())
```

The actual hashing logic lives in `cpv.hash_manifest`. ANY plugin can
ship `.cpv-self-hashes.json` by copying this 3-line wrapper. The format
is universal (per section A above).

### H. Universal pipeline files (canonical-pipeline skill expansion)

Every CPV-generated plugin / marketplace ships these files BYTE-FOR-BYTE
from a single source-of-truth in CPV:

| File | Purpose | Customizable? |
|------|---------|---------------|
| `scripts/publish.py` | Wrapper → cpv.publish | NO (1-line wrapper, identical) |
| `scripts/compute_cpv_self_hashes.py` | Wrapper → cpv.hash_manifest | NO (1-line wrapper) |
| `git-hooks/pre-push` | Calls publish.py only | NO (universal) |
| `git-hooks/pre-commit` | Lint + format check | NO (universal) |
| `cliff.toml` | git-cliff config | YES (per-plugin sections allowed) |
| `.github/workflows/validate.yml` | CI on push/PR | NO |
| `.github/workflows/notify-marketplace.yml` | Dispatch to marketplace | YES (env vars only) |
| `.github/workflows/release.yml` | GitHub release on tag | NO |
| `pyproject.toml` | Python deps + pytest config | YES |
| `.gitignore` | Standard ignores | YES (additions allowed) |
| `LICENSE` | License file | YES (license choice per plugin) |
| `README.md` | User-facing docs | YES (entirely per-plugin) |

`canonical-pipeline` skill is the documentation+enforcement layer. A
new helper `cpv-doctor --standardize` re-syncs the immutable files from
CPV's source of truth, leaving the `YES` files alone.

### I. Auto-discovery flow

When publish.py runs:

```
1. detect_repo_shape(cwd) → RepoShape
2. extract_config_from_tree(shape) → dict
3. validate_config(config) → list[Issue]  (fail-fast on missing required)
4. If shape == 'workspace-multi-git': prompt to pick subfolder, recurse.
5. If shape == 'submodule-bundle': verify+rebuild binary if needed.
6. Run the universal 14-gate pipeline (existing structure).
7. Refresh .cpv-self-hashes.json (issue #18 fix, now universal).
8. Commit, tag, push, release — same flow for every shape.
```

## Risks / tradeoffs

1. **Runtime CPV dependency** — every plugin needs CPV installed (one
   `claude plugin install` away). Not a concern for plugins on the
   official marketplace; potential issue for forks. Mitigation: provide
   a `--vendored` mode that bundles a minimal `cpv-publish-standalone`
   binary into the wrapper.

2. **Auto-detection failure modes** — bad assumptions about repo shape
   could publish to wrong place. Mitigation: every detected value is
   printed BEFORE the user is asked to confirm; `--dry-run` shows all
   inferences without touching git.

3. **Submodule bundling complexity** — building Rust binaries needs
   toolchain. Mitigation: detection only triggers the rebuild if the
   bundled binary is older than the submodule HEAD; otherwise trust
   the in-repo binary.

4. **Workspace-multi-git ambiguity** — a folder with N independent
   plugins might want to publish all in one shot. Mitigation: add
   `--all` flag that iterates each detected plugin sequentially.

## Implementation order (phased, each independently shippable)

1. **Phase A — Promote logic to importable modules** (foundation).
   Move `scripts/publish.py` → `cpv/publish.py`; same for hash manifest.
   `scripts/publish.py` becomes a wrapper. Existing CPV behaviour
   unchanged but the layout is in place.

2. **Phase B — Repo-shape detection** + auto-config extraction.
   `cpv.detect_shape()` and `cpv.extract_config()`. Wired into
   `cpv.publish.main()` so the existing 14-gate pipeline starts from
   auto-detected values instead of hardcoded ones.

3. **Phase C — Universal auth contract** (TRDD-b5e44619 Phase C). Eight
   auth surfaces, `/cpv-setup-auth` command/agent/skill triple.

4. **Phase D — Submodule-bundle support**. Detection + rebuild logic,
   manifest format extension, perfect-skill-suggester adopts the
   pattern as the canary case.

5. **Phase E — Workspace-multi-git support**. Numbered-table picker
   and `--all` flag.

6. **Phase F — Generate identical wrappers**. plugin-creator emits the
   3-line publish wrapper instead of the templated `gen_publish_py()`.
   Existing plugins migrate via `cpv-doctor --standardize`.

7. **Phase G — Universal hash-manifest format v2**. New format ships
   the `git`, `submodules`, `format` fields. `cpv_integrity.py` accepts
   both v1 and v2 for transition.

8. **Phase H — Canonical pipeline files** as templates. `cpv-doctor
   --standardize` re-syncs immutable files; `--check` reports drift.

Each phase is one PR; phases A and B are prerequisites for everything
else, but C/D/E can ship in any order after that.

   prompt to pick a subfolder, OR error out and require the user to
   `cd` first?
2. **Submodule rebuild trigger**: should `publish.py` rebuild the
   bundled binary AUTOMATICALLY when the submodule HEAD has advanced,
   OR only when the user passes `--rebuild-bundles`?
3. **Wrapper customization**: should the wrapper allow ZERO
   customization (truly identical bytes) OR allow a `pre_publish` /
   `post_publish` callback hook for plugin-specific extensions
   (NPM publish, container build, Docker push)?

   (`cpv-doctor --standardize` is interactive) OR forced
   (a CPV minor version bump migrates everyone)?
5. **Manifest v1 → v2 transition**: keep both formats supported for
   N releases, then drop v1; OR force-flip in one release with a
   migration helper?

Once these decisions are made, implementation begins with Phase A.

## Implementation rule of thumb

> *"If publish.py needs to know X, X must be auto-detectable from the
> tree. If X cannot be auto-detected, then either (a) X belongs in
> a config file already in the tree (e.g. plugin.json's `cpv` block),
> or (b) X is fundamentally per-user (auth tokens, GPG keys) and goes
> through `/cpv-setup-auth`."*

No environment variables. No "set this constant before publishing." No
"copy this template and fill in your values." Zero-config.

## Status — what shipped vs deferred (2026-05-10)

### Shipped this session (kraken on `wt/trdd-9065109a`)

**Phase B — repo-shape detection + auto-config extraction.** New module
`scripts/cpv_repo_shape.py` implements:
  - `detect_repo_shape(root) -> RepoShape` covering all seven kinds in
    the §B detection table (single-plugin, marketplace-hub,
    nested-monorepo, marketplace-in-plugin, workspace-multi-git,
    submodule-bundle, unknown). Layout takes precedence over submodule
    presence — a Layout C plugin with `.gitmodules` is reported as
    `marketplace-in-plugin` with `submodule_paths` populated, NOT as
    `submodule-bundle` (so the layout-aware publish dispatch is
    preserved).
  - `extract_config_from_tree(root, shape) -> RepoConfig` pulls plugin
    name+version (from `plugin.json`), GitHub remote owner+repo (from
    `git remote get-url origin`), marketplace owner+repo (from
    `notify-marketplace.yml`), submodule paths (from `.gitmodules`),
    and per-child shapes (workspace-multi-git only). All values are
    `None` when the signal is absent — never a fallback default.
  - `pick_workspace_child(shape, input_fn=...)` interactive picker for
    `workspace-multi-git`. The `input_fn` callable injection makes the
    picker test-driveable without mocking stdin.
  - `parse_owner_repo_from_remote(url)` URL parser (mirrored from
    `publish._parse_owner_repo_from_remote`) so callers don't have to
    reach into `publish.py` just for URL parsing.
  - CLI entry: `python scripts/cpv_repo_shape.py [<path>]` prints the
    detected shape + auto-extracted config in a stable plain-text
    format. Useful for users debugging "why does publish.py think my
    repo is X?" without dropping into a Python REPL.

**Phase G — hash-manifest format v2 schema helpers.** New module
`scripts/cpv_hash_manifest_v2.py` ships:
  - `build_v2_manifest(v1, *, git=None, submodules=None)` promotes a
    v1 manifest dict to v2: adds `version: 2`, `format:
    "cpv-hash-manifest-v2"`, optional `git` block (`tag`+`sha`+`remote`
    of the source commit), optional `submodules` block (per-path
    `url`+`sha`+`purpose`).
  - `normalize_to_files_dict(manifest)` reads either v1 OR v2 and
    returns the inner files map. Raises `KeyError` for missing
    `version`, `ValueError` for unsupported version. Backward-compat
    contract: existing v1 manifests stay valid.
  - `detect_format_version(manifest)` returns the manifest version
    (1, 2, or None for malformed input) without raising.
  - `SUPPORTED_VERSIONS = {1, 2}` and `V2_FORMAT_TAG =
    "cpv-hash-manifest-v2"` constants for downstream callers.

**Tests.** 46 new tests across `tests/test_cpv_repo_shape.py` (33) and
`tests/test_hash_manifest_v2.py` (13). Full suite: 4881 passing + 3
skipped (no regressions).
